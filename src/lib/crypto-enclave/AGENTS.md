## Password engine (wasm/rout-opaque)
- The OPAQUE (RFC 9807) + Argon2id password engine is one allocator-free Rust Wasm module (wasm/rout-opaque) with imported fixed memory per operation, zero-filled in finally; it runs only in the crypto worker and server-only handlers, and its loader refuses bytes that do not match the SHA-384 in opaque-wasm-pin.ts. Rebuild only with wasm/rout-opaque/build.sh under the toolchain pinned in its rust-toolchain.toml (official rustup build; distro builds of the same version are refused), update the pin in the same change, and keep .github/workflows/wasm-reproducible.yml green. Why: the shipped engine must be byte-for-byte traceable to its source, and the password and derived keys must never touch the UI thread or a growable heap.

## Anonymous booking engine (wasm/rout-zk)
- BBS / Blind BBS live in the allocator-free no_std Rust crate wasm/rout-zk and must stay byte-exact with every fixture in its tests/fixtures; external G1/G2 points pass on-curve, subgroup and identity checks before use, and secret comparisons use subtle. The browser may load it only after a pinned reproducible build exists (same rules as rout-opaque). Why: unpinned or unchecked curve code would break unlinkability guarantees silently.
- Booking pseudonyms come only from pseudonyms.ts via the worker op pseudonym.derive, kept equal to wasm/rout-zk/src/pseudonym.rs by a shared vector. Why: two implementations of one rule must not drift.
- Pedersen commitments and 64-bit range proofs exist only in wasm/rout-zk (pedersen.rs, bulletproofs.rs) behind the worker ops pedersen.commit, bulletproofs.prove_range and bulletproofs.verify_range (bulletproofs.ts via zk-engine.ts); generators are hash_to_curve points under the crate's fixed DST, outside generators are accepted only when equal to them, and proofs are bound to a caller context. zk-engine.ts refuses bytes that do not match zk-wasm-pin.ts (pinned from wasm/rout-zk/build.sh, same rebuild rules as rout-opaque); tests may substitute a pin only through vi.mock. Why: a second implementation or a swapped generator would silently break the capacity guarantee.
- Booking nullifiers are spent only through the worker ops smt.genesis / smt.insert_nullifier / smt.verify_non_membership / smt.verify_signed_root (smt.ts over wasm/rout-zk poseidon.rs + smt.rs): Poseidon constants come only from tools/poseidon_params.py and must match the reference fixture, the node store is untrusted, and a root counts only when signed by the member's own root key and not below the worker's high-water mark. Why: a database admin must be unable to edit, forge or roll back the set of spent nullifiers.
- Host credential keys are forward-secure and exist only in wasm/rout-zk forward_secure.rs behind the worker ops host_key.init / advance_epoch / sign_credential / chain / verify_epoch_credential (forward-secure.ts): the chain state starts from an engine-side random seed (never from a stored or device key), is held in the worker's HostKeyStore, is overwritten in place on every advance and leaves the worker only as an hsk envelope sealed to the member's own device key (owner decision 7f); only the current epoch signs, and verifiers accept an epoch key only via signed links from the anchor. Why: any surviving copy of an older state would let a later compromise forge earlier bookings.
- Anonymous presentations and capacity pools exist only in wasm/rout-zk anon.rs behind the worker ops anon_guest.*, anon_host.verify_presentation, host_key.sign_slot_credential and capacity.* (anon-booking.ts); guest nullifiers, seeds and prover blinds never leave the worker, and pool blindings derive from the device seed. Why: the host and the database see only public proof material and per-booking pseudonyms.
- The guest vault (guest-vault.ts) runs only in the crypto worker: guest master seed, SK_guest and the storage key come from the guest passkey's WebAuthn PRF (fallback: an assertion signature only when two assertions are byte-identical), and IndexedDB vault_guest_storage holds only { v, iv, ct } AES-256-GCM records padded to 4096-byte buckets; no guest state goes to localStorage, sessionStorage or the server. Why: a guest's bookings must survive a reload without any unencrypted copy on disk.
- The post-quantum double ratchet (Stap 8) exists only in wasm/rout-zk pq_ratchet.rs (ML-KEM-1024 + X25519 hybrid root step, HMAC chain, AES-256-GCM + HMAC in RVE2 envelopes, fixed STATE_LEN state committed only on success) behind the worker ops pq_ratchet.* (pq-ratchet.ts); session state lives only in the worker's PqSessionStore, is overwritten in place, is persisted only as AES-256-GCM records in IndexedDB vault_ratchet_sessions (pq-session-vault.ts, key HKDF from PRF seed || host_device_key seed, written before a step returns) and never sent to the server; an initiator session starts only from a prekey document that passes verifyPrekeyDocument, and published prekey documents live in Scaleway under users/<uid>/prekey-bundle.json, never in SQL. Why: one audited implementation, ratchet keys never reach the UI thread or Neon, and an unauthenticated bundle must never open a session.
